称重与余粮体系重构

从“食盆还剩多少”，追问到“宠物今天吃够了吗”。围绕当日进食量，重新组织称重、出粮与喂食信息。

01  追问问题

用户为什么需要知道余粮重量？

余粮显示偏差是项目的起点。我继续追问，用户查看这个数字，是为了做什么判断？往下拆解后，真正关心的是宠物当天吃了多少、是否吃够，以及接下来如何安排喂食。食盆余粮是回答这些问题的一个维度。

01 / SURFACE
余粮重量显示有偏差
这是被用户直接感知到的表面问题。
02 / ASK
用户为什么在意这个数字？
重量本身不是最终目标，需要继续追问它要支持什么判断。
03 / NEED
宠物今天吃了多少，是否吃够？
用户想理解的是一天中的进食情况，而不是某个时刻的孤立读数。
04 / PRODUCT GOAL
围绕当日进食情况构建体系
余粮、出粮与进食记录共同服务于这个目标。
02  目标重定义

从一个重量数字，到一天的进食情况

当目标转向当日进食情况，产品需要解释不同数据各自代表什么。我将设备出粮、宠物进食与食盆余粮分开表达，并把它们与当天的喂食安排联系起来。

Question at first
余粮显示存在偏差
keep asking
Product goal
帮助用户理解当日进食情况
出粮量设备投放了多少，说明喂食计划执行到哪里。
进食量宠物当天累计吃了多少，承接今日记录与事件。
余粮食盆当前还剩多少，作为理解当日状态的一个维度。
03  信息重组

把喂食过程组织成能理解的信息

围绕新的目标，首页区分累计出粮、累计进食和剩余待执行计划；今日记录承接进食统计与事件查看，余粮模块保留当前状态、克重和更新时间，让每一类信息都有明确用途。

Information model

累计进食

今日记录承接宠物当天的进食统计，让用户先看过程，再理解当前状态。

04  体系落地

让新逻辑覆盖完整使用过程

新体系同时覆盖新用户建档和老用户已有计划。我将信息录入、测试出粮、计划衔接与校准异常纳入流程，并拆解固件、插件与云端职责，推动多端按照统一规则实现。

New user path
信息录入→测试出粮→推荐计划
Existing user path
校准→测试出粮→既有计划衔接
APP插件录入信息、下发指令、展示状态和计划。
DEVICE固件执行出粮、采样并上报状态。
CLOUD云端处理档案、样本、判定与计划存储。

对复杂的余粮异常分支，先评估它是否影响今日出粮与进食统计，再决定处理优先级。

PM Takeaway

最关键的判断发生在方案设计之前：继续追问用户为什么需要这个数字。当问题推进到“宠物今天吃了多少、是否吃够”，需要设计的内容也扩展为围绕进食情况建立的一整套产品体系。
